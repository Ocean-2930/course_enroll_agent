# Frontend 제작 지침

## 목적

이 디렉터리의 프런트엔드는 `agents_lab_handoff/agents_lab.html`의 화면 표현과 상호작용 방식을 참고해 제작한다.

참고 파일:

```text
../../agents_lab_handoff/agents_lab.html
```

참고 대상은 다음으로 한정한다.

- 화면의 정보 구조와 시각적 위계
- 추천 항목을 탐색하는 방식
- 사용자가 입력하고 결과를 확인하는 흐름
- 드로어, 카드, 온보딩, 상태 피드백 등의 UI 패턴
- 데스크톱과 모바일의 반응형 표현

프런트엔드는 `../backend/main.py`의 FastAPI 서버가 실행 중인 환경을 기본으로 한다. 기존 n8n, Supabase, Gemini, Groq 연동 방식은 새 프런트엔드의 요구사항으로 간주하지 않는다. 이후 API와 데이터 모델이 확장될 수 있으므로 프런트엔드는 교체 가능한 API 경계를 갖도록 만든다.

현재 사용 가능한 API 목록과 화면 구성은 `../docs/PROJECT_STRUCTURE.md`를 기준으로 확인한다. 이 문서의 개별 예시가 그 내용과 어긋나면 `PROJECT_STRUCTURE.md`와 실제 코드가 우선한다.

## 기본 원칙

- 모든 사용자 노출 문구는 자연스러운 한국어로 작성한다.
- 텍스트 파일은 UTF-8로 저장한다.
- 화면은 “하나의 목적을 발견하고, 필요한 내용을 입력하고, 결과를 확인하는 앱”처럼 느껴져야 한다.
- 기존 HTML의 시각적 경험은 참고하되 400KB 이상의 단일 파일 구조를 그대로 복제하지 않는다.
- 스타일, 화면, 상태, 데이터, API 호출을 역할별로 분리한다.
- 서버 연결 상태는 실제 FastAPI `GET /ping`으로 확인한다.
- 아직 백엔드 API가 없는 기능은 목 데이터 또는 어댑터로 주요 화면 상태를 확인할 수 있게 한다.
- 화면에 API 키, 데이터베이스 키, 웹훅 주소 등의 비밀정보를 하드코딩하지 않는다.

## 화면의 핵심 사용자 흐름

프런트엔드는 다음 세 단계를 명확하게 표현해야 한다.

```text
발견 → 입력·조정 → 실행·결과
```

### 1. 발견

사용자가 현재 하고 싶은 일을 자연어로 입력하거나 추천 카드에서 선택한다.

표현 요소:

- 중앙의 핵심 질문 또는 검색 입력
- 현재 상황에 맞춘 추천 항목
- 추천 이유
- 실행을 유도하는 짧은 CTA
- 전체 기능을 분야별로 탐색할 수 있는 보조 영역

### 2. 입력·조정

선택한 기능에 필요한 값을 입력하고 결과 형식을 조정한다.

표현 요소:

- 기능명과 한 줄 설명
- 카테고리 및 신뢰 수준 배지
- 텍스트 입력, 붙여넣기, 선택, 표 형태 입력 등 목적에 맞는 폼
- 선택 가능한 결과 스타일
- 저장 방식이나 알림 등 해당 기능에 필요한 설정
- 실행 버튼

### 3. 실행·결과

실행 상태를 표시하고, 완료 후 결과를 목적에 맞는 구조로 보여준다.

표현 요소:

- 진행 중 상태
- 성공 결과
- 실패 및 재시도 상태
- 결과 복사
- 결과 저장
- 다음 행동 또는 연관 기능
- 일정, 체크리스트, 리포트 등 결과 유형별 전용 표현

## 전체 레이아웃

기본 페이지의 정보 순서는 다음을 따른다.

```text
상단 헤더
  ├─ 서비스 브랜드
  └─ 최소한의 사용자·환경 설정

메인 발견 영역
  ├─ 중앙 의도 입력
  ├─ 추천 노드 또는 추천 카드
  └─ 추천 새로고침·추천 기준

이어서 하기
  └─ 최근 실행하거나 저장한 작업

내 기능
  └─ 즐겨찾기 또는 고정한 기능

요약·리포트
  └─ 기록이 충분할 때만 표시

전체 기능 탐색
  ├─ 카테고리 필터
  ├─ 검색
  └─ 기능 카드 그리드

투명성·데이터 안내
  └─ 추천에 사용한 정보와 삭제·초기화 수단

하단 안내
```

페이지의 모든 영역을 처음부터 같은 중요도로 노출하지 않는다. 발견 영역을 가장 강하게 강조하고, 전체 기능 목록과 데이터 안내는 보조 위계로 둔다.

## 상단 헤더

- 브랜드는 짧고 명확하게 표시한다.
- 헤더 높이는 콘텐츠를 방해하지 않도록 작게 유지한다.
- 백엔드 연동 정보나 개발자용 API 키 입력은 일반 사용자 헤더에 노출하지 않는다.
- 개발 도구가 필요하면 개발 환경에서만 보이는 별도 패널로 분리한다.
- 모바일에서는 브랜드와 필수 동작만 남긴다.

## 메인 발견 영역

### 중앙 의도 입력

- 사용자가 무엇을 입력해야 하는지 설명하기보다 예시로 이해할 수 있게 한다.
- 예시: `이번 주 수강 신청 일정을 정리하고 싶어요`
- Enter 키와 실행 버튼을 모두 지원한다.
- 빈 입력, 검색 중, 추천 없음 상태를 각각 제공한다.
- 입력값은 화면에 다시 표시할 때 반드시 안전하게 이스케이프한다.

### 추천 표현

데스크톱에서는 중앙 입력 주변에 추천 항목을 배치하는 마인드맵형 표현을 사용할 수 있다.

- 중앙 입력을 가리지 않는다.
- 추천 항목 수가 변해도 겹치지 않는다.
- 연결선은 의미를 보조할 뿐 클릭을 방해하지 않는다.
- 가장 중요한 추천 1~3개를 시각적으로 크게 표현한다.
- 추천 카드에는 이름, 추천 이유, 신뢰 수준, CTA를 표시한다.

모바일에서는 마인드맵을 억지로 축소하지 않는다.

- 연결선을 숨긴다.
- 추천을 1열 또는 2열 카드 목록으로 전환한다.
- 카드 터치 영역은 최소 44px 이상 확보한다.

추천 UI가 복잡해질 경우 원형 배치보다 읽기 쉬운 카드 그리드를 우선한다.

## 전체 기능 탐색

- 왼쪽 카테고리, 오른쪽 결과 목록 구조를 기본으로 한다.
- 데스크톱 카테고리 영역은 필요하면 sticky로 유지한다.
- 모바일에서는 카테고리를 가로 스크롤 칩 또는 접을 수 있는 필터로 전환한다.
- 각 기능 카드는 다음 정보를 포함한다.
  - 아이콘
  - 기능명
  - 한 줄 가치 설명
  - 필요 시 신뢰·민감도 수준
- 카테고리별 개수와 현재 검색 결과 개수를 표시한다.
- 결과가 없을 때는 조건을 초기화할 수 있는 동작을 제공한다.

## 작업 드로어

기능을 선택하면 데스크톱에서는 오른쪽 드로어로 작업 화면을 연다.

- 배경 오버레이를 표시한다.
- 닫기 버튼, `Escape`, 오버레이 클릭으로 닫을 수 있게 한다.
- 드로어가 열리면 내부 제목 또는 첫 입력에 포커스를 이동한다.
- 드로어가 닫히면 열기 전 요소로 포커스를 복원한다.
- 본문은 독립적으로 스크롤할 수 있어야 한다.
- 실행 결과도 같은 작업 맥락 안에 표시한다.

모바일에서는 드로어를 전체 화면 시트 또는 별도 화면처럼 표현한다.

## 입력 폼

기능 정의에 따라 입력 UI를 동적으로 구성할 수 있어야 한다.

지원할 기본 입력 유형:

- 한 줄 텍스트
- 여러 줄 텍스트
- 선택 상자
- 날짜 및 시간
- 숫자
- 체크박스
- 반복 가능한 행
- 간단한 표
- 붙여넣기 전용 입력
- 타임라인 또는 할 일 목록

입력 필드 원칙:

- 모든 입력에는 연결된 `label`이 있어야 한다.
- placeholder는 라벨을 대신하지 않는다.
- 필수 여부와 오류를 명확히 표시한다.
- 예시 값이 실제 사용자 데이터로 오인되지 않게 한다.
- 민감한 입력에는 저장 범위와 사용 목적을 가까이 표시한다.
- 실행 전에 필요한 값만 검증하고 불필요한 입력을 강요하지 않는다.

## 실행 상태

실행 버튼은 다음 상태를 구분한다.

```text
idle
validating
loading
success
error
```

- 실행 중에는 중복 제출을 방지한다.
- 버튼 안에 스피너와 `실행 중…` 문구를 표시한다.
- 로딩이 길어질 경우 현재 단계나 대기 안내를 제공한다.
- 오류 메시지는 사용자가 다음에 할 행동을 알 수 있게 작성한다.
- 재시도할 때 기존 입력을 유지한다.
- 네트워크 오류와 입력 오류를 같은 메시지로 표현하지 않는다.

## 결과 표현

결과를 모두 일반 텍스트 상자에 넣지 않는다. 결과 유형에 따라 전용 UI를 사용한다.

지원할 결과 표현:

| 결과 유형 | 표현 방식 |
|---|---|
| 일반 설명 | 제목·문단·목록이 있는 읽기 화면 |
| 일정 | 날짜·요일·시간별 일정 카드 |
| 체크리스트 | 직접 체크 가능한 목록 |
| 분류 결과 | 중요도 또는 상태별 그룹 |
| 답변 초안 | 복사하기 쉬운 메시지 카드 |
| 리포트 | 핵심 수치 타일과 상세 설명 |
| 진행 기록 | 진행률, 연속 기록, 다음 목표 |
| 표 | 가로 스크롤 가능한 반응형 표 |

LLM 또는 외부 API가 반환한 문자열은 그대로 `innerHTML`에 삽입하지 않는다. 마크다운을 지원할 경우 검증된 렌더러와 HTML 정화 과정을 사용한다.

결과 영역에는 필요에 따라 다음 동작을 제공한다.

- 결과 복사
- 요약 저장
- 다시 실행
- 입력 수정
- 다음 기능 열기
- 캘린더 내보내기
- 공유

외부 전송이나 예약 확정 등 실제 영향을 주는 동작은 결과 생성과 분리하고 사용자 승인을 한 번 더 받는다.

## 이어서 하기와 즐겨찾기

- 최근 작업은 최대 개수를 제한해 표시한다.
- 기능명, 마지막 사용 시각, 짧은 결과 요약을 보여준다.
- 즐겨찾기는 카드 안에서 즉시 추가·해제할 수 있게 한다.
- 즐겨찾기 버튼과 카드 열기 동작이 충돌하지 않게 이벤트를 분리한다.
- 데이터가 없으면 빈 박스만 두지 말고 첫 행동을 안내한다.

## 온보딩

온보딩은 짧은 단계형 흐름으로 구성한다.

권장 수집 정보:

- 역할
- 현재 목표
- 관심 분야
- 선호하는 시작 방식

원칙:

- 건너뛰기를 제공한다.
- 이전 단계로 돌아갈 수 있게 한다.
- 한 단계에 너무 많은 선택지를 보여주지 않는다.
- 선택 이유와 추천에 어떻게 사용되는지 설명한다.
- 완료 후 바로 개인화된 추천 화면을 보여준다.

## 추천 근거와 데이터 투명성

- 추천에 사용한 역할, 관심사, 최근 작업 등을 사용자가 확인할 수 있게 한다.
- 특정 추천 숨기기와 관심도 낮추기를 구분한다.
- 저장된 로컬 데이터를 초기화할 수 있게 한다.
- 삭제는 확인 절차를 거치며 삭제 범위를 구체적으로 적는다.
- 현재 백엔드에는 저장 API가 없으므로 실제 동기화가 되는 것처럼 표현하지 않는다.

## 상태 관리

다음 상태를 서로 분리한다.

- 서버에서 받은 데이터
- 사용자 입력 중인 폼 상태
- 화면 열림·닫힘 등의 UI 상태
- 최근 사용·즐겨찾기 등의 로컬 상태
- 실행 중 상태와 오류

전역 변경 가능한 단일 객체에 모든 상태를 넣지 않는다. 상태 변경 후 어느 화면을 다시 그려야 하는지 수동으로 추적하는 구조를 피한다.

현재 구현된 서버 상태 확인은 실제 API를 사용하고, 아직 구현되지 않은 기능은 다음과 같은 프런트엔드 인터페이스를 기준으로 목 구현을 둔다.

```ts
interface HealthService {
  ping(): Promise<{ status: "ok" }>;
}

interface AgentService {
  searchIntent(query: string): Promise<Recommendation[]>;
  runAgent(request: RunAgentRequest): Promise<AgentResult>;
}

interface UserStateService {
  loadProfile(): Promise<UserProfile | null>;
  saveProfile(profile: UserProfile): Promise<void>;
  loadRecentTasks(): Promise<RecentTask[]>;
  saveResult(result: SavedResult): Promise<void>;
}
```

실제 URL, 인증 헤더, 데이터베이스 테이블 이름은 화면 컴포넌트에서 알지 못하게 한다. 화면 컴포넌트는 `HealthService`를 통해서만 서버 상태를 확인한다.

## 로컬 저장

- 현재 저장 API가 없으므로 즐겨찾기와 임시 입력을 유지해야 한다면 localStorage를 사용할 수 있다.
- 저장 키에는 버전을 포함한다.
- JSON 파싱 실패 시 안전한 기본값으로 복구한다.
- 민감한 원문은 기본적으로 localStorage에 저장하지 않는다.
- 저장 데이터 구조를 변경할 때 마이그레이션 또는 초기화 정책을 마련한다.

## 반응형 기준

최소한 다음 화면 폭을 확인한다.

- 360px 모바일
- 768px 태블릿
- 1024px 작은 데스크톱
- 1440px 데스크톱

모바일 전환 원칙:

- 사이드바 → 필터 칩 또는 접이식 필터
- 오른쪽 드로어 → 전체 화면 시트
- 3열 카드 → 1열 카드
- 원형 추천 배치 → 목록
- 넓은 표 → 가로 스크롤
- 부가 설명 → 접을 수 있는 상세 정보

가로 스크롤이 전체 페이지에 발생하지 않게 한다.

## 시각 디자인

기존 화면의 방향을 참고한다.

- 밝은 중성 배경
- 흰색 카드
- 보라색 계열의 주요 브랜드 색상
- 둥근 카드와 버튼
- 얕은 그림자와 명확한 테두리
- 성공, 경고, 민감도 상태별 구분색
- 이모지는 의미를 보조하는 수준으로 사용

색상만으로 상태를 전달하지 않는다. 텍스트, 아이콘, 배지를 함께 사용한다.

디자인 토큰을 정의해 일관되게 사용한다.

```css
:root {
  --color-brand: ...;
  --color-brand-soft: ...;
  --color-text: ...;
  --color-muted: ...;
  --color-border: ...;
  --color-surface: ...;
  --radius-card: ...;
  --shadow-card: ...;
}
```

## 접근성

- 모든 버튼은 실제 `button` 요소를 사용한다.
- 링크와 버튼의 역할을 혼용하지 않는다.
- 키보드만으로 모든 주요 흐름을 사용할 수 있어야 한다.
- 포커스 표시를 제거하지 않는다.
- 드로어와 모달에는 적절한 ARIA 속성과 포커스 트랩을 적용한다.
- 입력 오류는 색상 외에 문구로 제공한다.
- 로딩과 결과 완료 상태는 필요하면 `aria-live`로 알린다.
- 텍스트와 배경의 명도 대비를 확보한다.
- `prefers-reduced-motion`을 존중한다.

## 보안

- 외부 입력과 모델 출력은 신뢰하지 않는다.
- 사용자 입력을 HTML 문자열에 삽입할 때 이스케이프한다.
- 모델 결과를 렌더링하기 전에 정화한다.
- 외부 링크에는 필요한 경우 `target="_blank"`와 `rel="noopener noreferrer"`를 사용한다.
- API 키, Supabase anon key, n8n Webhook 주소를 소스에 직접 넣지 않는다.
- 운영자 기능은 URL 파라미터나 localStorage 값만으로 권한을 부여하지 않는다.

## 백엔드와의 경계

백엔드는 다음 명령으로 `127.0.0.1:8000`에서 실행된다고 가정한다.

```text
../backend/runserver.bat
```

서버 상태 확인 계약:

```http
GET /ping
GET /api/health
```

성공 응답:

```json
{
  "status": "ok"
}
```

프런트엔드는 시작 시 또는 서버 상태 확인이 필요한 시점에 이 API를 호출할 수 있다. 응답의 HTTP 상태가 성공 범위이고 JSON의 `status`가 `ok`이면 연결된 상태로 판단한다.

업무 API는 `/api` prefix 아래에 아카데미·수강권 종류·수강생·보유 수강권·수강 기록 CRUD와 조회 전용 집계(`/analytics`, `/worklists`, `/checks`)가 구현돼 있다. 전체 목록과 계약은 `../docs/PROJECT_STRUCTURE.md`와 `/docs`(OpenAPI)를 본다.

화면 코드는 `fetch()`를 직접 호출하지 않고 `assets/api.js`의 `window.CourseApi` 어댑터만 사용한다. 새 백엔드 엔드포인트를 화면에서 쓰게 되면 어댑터에 메서드를 먼저 추가한다.

API 기본 주소는 화면 코드에 반복해서 쓰지 않는다. 환경 설정 또는 API 클라이언트 한 곳에서 관리한다.

```ts
const API_BASE_URL =
  import.meta.env.VITE_API_BASE_URL ?? "http://127.0.0.1:8000";
```

사용하는 빌드 도구가 Vite가 아니라면 해당 환경의 구성 방식을 사용하되 같은 원칙을 지킨다. 로컬 프런트엔드와 백엔드의 origin이 다르면 개발 프록시를 우선 사용하고, 필요할 경우 백엔드 CORS 설정을 별도 협의한다.

현재 단계에서는 다음을 구현하거나 가정하지 않는다.

- n8n 워크플로우 구조
- Supabase 테이블 구조
- 익명 `device_id` 인증
- Gemini/Groq 폴백
- 기존 `/webhook/agent1000/*` 경로
- 브라우저에서 LLM API 직접 호출

프런트엔드는 API 어댑터를 통해서만 데이터를 요청한다. 아직 API가 없는 기능은 목 응답으로 다음 상태를 모두 재현할 수 있어야 한다.

- 추천 성공
- 추천 없음
- 실행 중
- 실행 성공
- 입력 오류
- 서버 오류
- 네트워크 오류
- 저장 성공
- 저장 실패

## 구현 완료 기준

- 첫 화면에서 사용자가 무엇을 해야 하는지 즉시 이해할 수 있다.
- 추천 선택부터 결과 확인까지 흐름이 끊기지 않는다.
- 모든 주요 상태에 빈 화면, 로딩, 성공, 오류 표현이 있다.
- 데스크톱과 모바일에서 핵심 기능을 동일하게 사용할 수 있다.
- 실제 `GET /ping`으로 FastAPI 서버 연결 상태를 확인할 수 있다.
- 화면이 사용하는 데이터는 모두 `window.CourseApi`를 거친다.
- 아직 API가 없는 기능만 목 데이터로 표현하고, 실제 저장되는 것처럼 보이게 하지 않는다.
- 백엔드 URL이나 비밀정보가 UI 코드에 하드코딩되어 있지 않다.
- 사용자 입력과 외부 결과가 안전하게 렌더링된다.
- 키보드 탐색과 포커스 이동이 정상 동작한다.
- 기존 `agents_lab.html`의 단일 파일 구조를 그대로 복제하지 않는다.
